# PRD: Macro Radar как проверяемый навигатор по экономике Казахстана

Статус: draft for decision
Дата: 12.09.2026
Владелец решения: Bagdat
Владелец продукта: JB Solutions
Связанный план: `docs/ROADMAP-macroradar.md`
Статус реализации на 23.09.2026: vertical slice «Стоимость денег» не начат. Отгружено вне фаз: source registry (часть фазы 0, 12.09), Energy Balance Monitor (13.09), Industry Radar (22.09). Health Radar собран в ветке `health-radar` репозитория macroradar. Baseline в разделе 3 зафиксирован на 12.09.2026.

## 1. Решение

Macro Radar должен отвечать на два вопроса: что изменилось и что уже известно о ближайших событиях. Рекомендуемый первый срез: «Стоимость денег для бизнеса». Он соединяет базовую ставку, инфляцию, календарь решений НБРК и календарь публикаций БНС на одном экране.

Факт, официальный прогноз и расчёт JB Solutions нельзя смешивать в одну линию. Каждый слой получает свой визуальный код, дату наблюдения, дату публикации и прямую ссылку на первоисточник. Если источник не обновился, пользователь видит возраст факта, а не свежую дату пересборки страницы.

Сначала нужно привести в порядок происхождение и свежесть всех опубликованных рядов и наборов. Интерактивная графика начинается после source gate фазы 0. Иначе красивый график усиливает ложное ощущение актуальности.

## 2. Проблема

Сайт уже собирает данные ежедневно, но ежедневная дата сборки не означает ежедневную актуальность показателя. Например, текущий файл КГД собран 12.09.2026, при этом динамика относится к 2024 году, а структура поступлений к марту 2025 года. Справочник ставок тоже пересобирается ежедневно, хотя его содержательная дата хранится отдельно в `reviewed_at`.

Для посетителя это создаёт три риска:

1. дата технической сборки воспринимается как дата наблюдения;
2. сохранённый прошлый ряд выглядит свежим после успешной пересборки;
3. прогноз, ожидание и сценарий могут восприниматься как одинаково достоверные данные.

Продуктовая задача: показать историю, ближайшие известные события и границу неизвестного без ложной точности.

### 3.3 Текущая техническая архитектура

Текущий production flow подтверждён кодом и workflow:

```text
jbs-finance/macroradar GitHub repo
  -> checkout ETL в workflow сайта
  -> generated JSON и HTML в website repo
  -> commit latest artifacts в website repo
  -> Next static export в out/
  -> Cloudflare Pages
```

ETL code не живёт в website repo. Workflow берёт его из `jbs-finance/macroradar`, выполняет сборщики, пересобирает статические страницы и обновляет market widget. Затем latest artifacts коммитятся в website repo. `next build` создаёт static export, каталог `out/` публикуется в Cloudflare Pages.

Evidence: `.github/workflows/update-pulse.yml:41-129,209-240`, `next.config.ts:15`, `.github/workflows/deploy.yml:77-82`.

`raw/` указан в `.gitignore` ETL repo. В GitHub Actions частично кэшируются файлы КГД через `macroradar/raw`. Сборщик КГД повторно использует локальный файл не дольше 7 дней. Retention и eviction GitHub Actions cache не являются storage SLA, immutable archive или полной revision history. Остальные raw responses могут существовать во время запуска, но текущий production contract не сохраняет их как долговечную доказательную базу.

Macro Radar сейчас не использует D1. Binding `COURSE_DB` в `wrangler.toml` относится к курсам и не входит в data flow Macro Radar. Его нельзя использовать или описывать как существующее хранилище радара.

## 4. Пользователи и JTBD

### 4.1 Руководитель малого и среднего бизнеса

Когда меняются ставка, инфляция или курс, хочет быстро понять направление давления на кредит, цены и оборотный капитал. Ему нужен вывод и контекст, а не набор отдельных статистических таблиц.

### 4.2 Финансовый директор или аналитик

Перед обновлением бюджета или прогноза хочет проверить последний факт, историю пересмотров и дату следующего официального события. Ему нужны исходные ряды, единицы измерения и прослеживаемая формула производного показателя.

### 4.3 Предприниматель, который изучает рынок

Хочет увидеть, что изменилось за выбранный период, сравнить темы и открыть первоисточник. Ему не нужен технический текст на первом экране.

### 4.4 Редактор JB Solutions

Хочет публиковать объяснение без ручного копирования дат и без риска выдать старый факт за новый. Ему нужны автоматические статусы, блокирующие гейты и журнал ревизий.

## 5. Цели и границы

### 5.1 Цели

1. Показать прошлую динамику, изменения и пересмотры по каждому ключевому индикатору.
2. Показать только известный forward layer: официальные календари и опубликованные официальные прогнозы.
3. Дать посетителю интерактивное исследование ряда без потери статического, доступного представления.
4. Сделать дату и происхождение каждого значения проверяемыми.
5. Обеспечить регулярное обновление, контролируемое по ожидаемой дате следующего выпуска.

### 5.2 Не входит в scope

- персональная инвестиционная, юридическая или налоговая рекомендация;
- предсказание курса, ставки или инфляции моделью без раскрытого сценария;
- consensus в P0 и P1;
- загрузка runtime, шрифтов или chart library со стороннего CDN;
- регистрация пользователя, кабинет и персональные watchlists в первой версии;
- новая плитка или вкладка «Методика»;
- реализация кода в рамках этого документа.

## 6. Информационная архитектура

### 6.1 Хаб `/macroradar/`

Хаб сохраняет пять тематических плиток. На нём добавляется компактный блок «Что изменилось» с тремя последними проверенными изменениями. Блок ведёт на соответствующие страницы индикаторов.

Методика остаётся отдельной страницей `/macroradar/methodology/`. Ссылка на неё находится в footer и в паспорте данных. Плитки и вкладки для методики не добавляются.

### 6.2 Тематическая страница `/macroradar/macro/`

Первый экран отвечает на вопрос о текущем режиме. Далее идут:

1. «Что изменилось»: дельты по выбранному периоду;
2. «Взгляд назад»: интерактивный ряд и события;
3. «Что известно впереди»: календарь и официальные прогнозы;
4. «Для бизнеса»: интерпретация с границами применимости;
5. паспорт данных и ссылка на методику.

### 6.3 Страница индикатора

Рекомендуемый адрес первого vertical slice: `/macroradar/macro/cost-of-money/`. Страница открывается из блока на тематической странице, но не становится новой верхнеуровневой вкладкой.

## 7. Демонстрация «Стоимость денег для бизнеса»

### 7.1 Вопрос

Насколько жёсткими были денежные условия, что изменилось и какие официальные события уже стоят в календаре?

### 7.2 Слои «Взгляд назад»

| Слой | Данные | Представление | Маркировка |
|---|---|---|---|
| Базовая ставка | Решения НБРК | Сплошная ступенчатая линия | Наблюдаемый факт |
| Инфляция год к году | Ежемесячные публикации БНС | Сплошная линия | Наблюдаемый факт |
| Реальный policy gap | Базовая ставка минус инфляция год к году | Отдельная тонкая линия или нижняя панель | Расчёт JB Solutions |
| События | Решения НБРК и публикации инфляции | Маркеры на временной оси | Официальное событие |
| Пересмотры | Сохранённые vintages одного наблюдения | Значок ревизии и diff | Наблюдаемый пересмотр |

`Реальный policy gap` не называется реальной стоимостью кредита. Это производный ориентир. Формула показывается рядом с графиком.

Переключатели периода: 12 месяцев, 3 года, 5 лет, весь доступный ряд. Пользователь может включить или выключить линии, навести курсор или перевести keyboard focus на точку, открыть таблицу и перейти к источнику.

### 7.3 Слои «Посмотреть вперёд»

P0 показывает:

- дату следующего решения по базовой ставке из календаря НБРК;
- ожидаемую дату публикации инфляции из календаря БНС;
- опубликованный официальный прогноз НБРК, если у него есть действующий период и прямая ссылка.

Прогноз не продолжается за опубликованный горизонт. Просроченный прогноз скрывается из основного графика и остаётся в архиве.

Consensus не включается в P0. Он допускается только после решения по лицензии, методике отбора, частоте обновления и праву публикации. Сценарий JB Solutions появляется позже как диапазон, а не как точечное обещание.

### 7.4 Ответ для бизнеса

Под графиком размещается короткий вывод по последнему проверенному факту. Текст объясняет, на какие решения может влиять режим ставки: цена нового долга, рефинансирование, hurdle rate и оборотный капитал. Это объяснение, а не персональная рекомендация.

Критичный показатель получает один первичный источник. Второй независимый источник используется для reconciliation, а не для тихой подмены. При расхождении публикация нового значения блокируется до разбора.

## 10. Контракт свежести, происхождения и ревизий

### 10.1 Обязательные поля

| Поле | Смысл |
|---|---|
| `generated_at` | Когда собран итоговый artifact |
| `fetched_at` | Когда получен ответ конкретного источника |
| `observed_period` | Период, к которому относится значение |
| `source_published_at` | Когда источник опубликовал конкретный выпуск |
| `next_expected_at` | Когда ожидается следующий выпуск по официальному календарю или правилу cadence |
| `source_url` | Прямая ссылка на первичный выпуск или API query |
| `source_id` | Устойчивый идентификатор источника из registry |
| `transform_version` | Версия ETL, зафиксированная commit SHA или release tag |
| `raw_sha256` | Хеш сохранённого raw artifact, обязателен для первого vertical slice, затем для серий с revision history |
| `status` | `fresh`, `due`, `late`, `stale`, `blocked`, `manual_review` |
| `revision_id` | Идентификатор vintage для сравнения пересмотров |

### 10.2 Правила свежести

1. Freshness считается от `observed_period` и `next_expected_at`, а не от `generated_at`, для всех опубликованных рядов и наборов.
2. Порог задаётся в registry для каждой опубликованной серии и каждого набора с учётом cadence.
3. После `next_expected_at` действует явное grace window. Его длину утверждает владелец данных для серии.
4. Истёкшее grace window переводит серию в `late` или `blocked`.
5. Last known good разрешён только с видимой датой исходного наблюдения и причиной fallback.
6. Ручной источник не становится свежим от автоматической пересборки.
7. Календарное событие закрывается фактической публикацией. Если публикация не появилась, событие получает статус `late`.

### 10.3 Ревизии

Первый vertical slice хранит raw artifact и нормализованный vintage для каждого успешного сбора. Остальные серии подключаются к этому контракту при добавлении revision history. Изменение уже опубликованного периода записывается в revision log: старое значение, новое значение, абсолютная и относительная дельта, источник, дата обнаружения. График показывает значимые ревизии, а паспорт данных даёт полный журнал.

### 10.4 Целевая техническая архитектура

| Слой | Где живёт | Что хранит | Статус решения |
|---|---|---|---|
| ETL code | GitHub repo `jbs-finance/macroradar` | Collectors, transforms, source registry, schemas, fixtures и tests | Целевой контракт на базе текущего repo |
| Latest public artifacts | Website repo `jbs-finance` | Последние проверенные HTML и normalized JSON | Сохраняется текущий подход |
| Private evidence store | Private object storage | Immutable raw snapshots, normalized vintages, checksums и revision manifests | Требует решения; Cloudflare R2 рекомендуется, но сейчас не используется Macro Radar |
| Revision manifest | Сначала JSON objects в private object storage | Индекс vintages, source dates, transform version и revision links | D1 не нужен для первой версии |
| Query index | D1 или другая база | Поиск по большой истории и операционные выборки | Отложено до подтверждённой потребности |
| Interactive runtime | Cloudflare Pages вместе со static export | Self-hosted JavaScript с content hash | Новый слой фазы 1 |
| Research workspace | NotebookLM | Публичные official sources, research questions и черновые выводы | Только исследование, не production storage |

Рекомендация по private evidence store: Cloudflare R2. Основание: сайт уже публикуется в Cloudflare, объектное хранилище подходит для versioned keys и отделяет доказательную базу от public Git. Это архитектурная рекомендация, а не описание текущего состояния. Перед реализацией R2 сравнивается с альтернативой по стоимости, retention, восстановлению, доступам и portability.

Предлагаемые prefixes:

```text
raw/{source_id}/{yyyy}/{mm}/{dd}/{run_id}/{artifact_name}
normalized/{series_id}/{observed_period}/{revision_id}.json
manifests/revisions/{series_id}.json
runs/{run_id}/manifest.json
```

Иммутабельность обеспечивается новым key на каждый run и запретом overwrite в CI policy. Lifecycle rules определяются отдельно для raw, normalized vintages и run manifests. Latest public JSON не читается браузером напрямую из private storage: он проходит validation и попадает в website repo через текущий publish flow.

### 10.5 Public и private границы

| Public | Private |
|---|---|
| Latest проверенные HTML и normalized JSON | Полные raw responses и исходные workbooks |
| Self-hosted hashed JavaScript | Исторические normalized vintages до решения о public archive |
| Source URL, observation period, publication date, fetch date, transform version | Revision manifests с внутренними run ids и диагностикой |
| Видимый freshness status и formula lineage | Ошибочные, quarantined и непрошедшие reconciliation artifacts |
| Методика и ограничения | Credentials, tokens, bucket names при наличии security reason, alert endpoints |

Bucket не получает public hostname. Browser не получает credentials и не читает private evidence store. GitHub Actions получает минимально необходимые secrets через защищённое хранилище CI. Credentials не пишутся в repo, generated HTML, logs, NotebookLM или task briefs.

NotebookLM получает только публичные official sources. Client data, секреты, внутренние credentials и непубличные финансовые данные не передаются NotebookLM, Gemini или другим cloud models.

D1 не добавляется заранее. Revision manifest сначала остаётся JSON в private object storage. Переход к D1 требует наблюдаемой задачи, которую неудобно или дорого решать object listing и manifests: сложный поиск, массовая выборка vintages, пользовательские watchlists или операционная аналитика.

## 12. Требования к интерактивной графике

### 12.1 Поведение

- синхронный crosshair для ставки и инфляции;
- zoom через контролы периода, без зависимости от wheel gesture;
- кнопка «Показать таблицу» рядом с графиком;
- события открываются в доступной detail panel;
- URL сохраняет выбранный период и включённые серии без персональных данных;
- источник точки открывается в новой вкладке с явным названием источника.

### 12.2 Accessibility

- все controls доступны с клавиатуры в логичном порядке;
- focus indicator имеет достаточный визуальный контраст;
- chart summary сообщает направление, последний период и активные серии;
- сложный график имеет табличное или структурированное текстовое описание по подходу [W3C WAI](https://www.w3.org/WAI/tutorials/images/complex/);
- интерактив используется только там, где выбор пользователя меняет прочтение данных, по [guidance ONS](https://service-manual.ons.gov.uk/data-visualisation/guidance/interactive-charts-and-animations);
- interactive animation учитывает [WCAG 2.2 animation from interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html);
- цвета дублируются типом линии, подписью и формой маркера;
- touch target и layout проверяются на mobile viewport;
- screen reader не читает каждую точку подряд без запроса пользователя.

### 12.3 Offline и no-JS fallback

HTML содержит server-generated вывод, последние значения, таблицу и ссылки на источники. Интерактивный слой улучшает этот baseline. Если script не загрузился, смысл страницы сохраняется. Если JSON недоступен, остаётся последний проверенный server-generated snapshot с явной датой.

### 12.4 CSP

Текущий blanket `script-src 'none'` меняется только на страницах с интерактивностью. Допускается self-hosted JavaScript с content hash в имени файла и `script-src 'self'`. Inline script, `unsafe-eval`, внешний CDN и third-party runtime запрещены. Изменение сопровождается отдельным CSP contract test.

### 15.1 Отраслевые радары

Отраслевой радар не должен быть новой плиткой с набором общих цифр. Он получает один повторяемый вопрос, стабильные источники и свою доказанную аудиторию.

Рекомендация состоит из трёх ступеней. Сначала можно проверить локальный узкий pilot `Energy Production Monitor`, потому что он переиспользует текущие adapters и сочетает дневной внешний benchmark с месячными сигналами. Оба направления проходят непубличный discovery после core data trust layer. До завершения core slice gates probe, интервью и prototype остаются локальными. На сайте не создаётся даже скрытый route. #### Общий discovery gate отрасли

GO из непубличного discovery в подготовку отраслевого pilot возможен, если для каждого core metric подтверждены: хотя бы один machine-readable official source, опубликованная cadence, revision policy, стабильность доступа в 90-day probe, owner и fallback. Период 90 дней является design requirement JB Solutions, а не исторически подтверждённой стабильностью источника. Публикация pilot всё равно ждёт core phase gates и решения фазы 4.

Полный power-market и tariff контур получает отдельный STOP до подтверждения устойчивых machine-readable источников. Текущая evidence base не подтверждает стабильный feed тарифов, планов мощностей или real-time рынка.

## 16. Риски и контроль

| Риск | Последствие | Контроль |
|---|---|---|
| Источник меняет HTML или workbook | Parser возвращает пустоту или смещённые поля | Raw archive, schema tests, reconciliation, last known good |
| Старая дата скрывается новым `generated_at` | Пользователь принимает старый факт за текущий | Раздельные даты и status от observation age |
| Официальный прогноз выглядит как факт | Ложная уверенность | Отдельный type, line style, author и horizon |
| Интерактив скрывает данные от screen reader | Часть аудитории не получает содержание | Summary, table, keyboard tests, screen reader audit |
| CSP ослабляется слишком широко | Растёт поверхность атаки | Self-hosted bundle, no inline, no CDN, отдельный test |
| Consensus нарушает лицензию | Правовой и репутационный риск | Не включать до утверждённой лицензии |
| JBS scenario воспринимается как обещание | Репутационный риск | Range, assumptions, version и явная маркировка |
| Ежедневный workflow создаёт шум commit history | Сложнее отличить содержательное обновление | Коммитить только изменение normalized content и отдельный provenance log |

| Решение | Рекомендация | Цена ошибки |
|---|---|---|

## 18. Definition of done продукта

Первая версия готова, когда source registry, observation-age freshness и negative false-fresh tests покрывают все уже опубликованные серии и наборы. После этого один vertical slice проходит полную цепочку: первичный источник, raw artifact, normalized vintage, freshness status, revision log, статический HTML, интерактивный график, таблица, screen reader summary, CSP test, missed-update alert и прямые ссылки на источники. ## 20. Low-token execution architecture

Цель execution architecture: отдавать повторяемую работу детерминированным инструментам и локальным моделям, а дорогую модель использовать там, где ошибка меняет смысл данных, безопасность или архитектуру. Экономия tokens не снижает evidence bar.

### 20.1 Маршрутизация работы

| Уровень | Инструменты | Разрешённые задачи | Не передавать |
|---|---|---|---|
| Детерминированный | Bash, Python, `jq`, `rg`, project tests | Inventory, schema diff, source probe, extraction, fixture generation по явной схеме, link checks, повторяемые проверки | Решения о смысле показателя и trust classification |
| Локальный основной | Ollama `qwen3.5:9b`, Q4_K_M, image size около 6.6 GB | Предлагаемый lane: классификация, draft registry, draft fixtures, cleanup документации, простые tests в точных границах | Автономная архитектура, финансовая семантика, сложная multi-repo orchestration |
| Локальный лёгкий | Ollama `qwen3:4b-instruct` | Предлагаемый lane: boilerplate, extraction, переименование полей по mapping, простые таблицы | Неопределённые задачи и финальная приёмка |
| Локальный языковой | Ollama `kazllm:8b` | Помощь с формулировками RU/KZ после фиксации фактов | Source-trust решения, цифры, нормы и самостоятельный fact-check |
| Ограниченный coding lane | Kimi Code CLI 0.28.0 | Локальные code edits по точному brief, integration glue, tests и механические multi-file changes | Самостоятельное изменение architecture, scope или data semantics |
| Optional large-context lane | Gemini CLI, сейчас не установлен | Read-only audit большого контекста или frontend draft, только при зафиксированной причине | Secrets, client data и финальная приёмка |
| Сильная модель | Primary architecture and review agent | Architecture, source trust, financial semantics, security, conflict resolution и финальная приёмка | Рутинная extraction, если её закрывает script или локальная модель |

Детерминированный discovery запускается первым. Bash, Python, `jq` и `rg` не расходуют model tokens на повторное чтение и дают воспроизводимый artifact. Model lane получает уже отфильтрованный контекст, diff и failing checks.

Рабочая машина: MacBook Air M5, 10 cores, 16 GB RAM. У `qwen3.5:9b` в Q4_K_M размер Ollama image около 6.6 GB. Peak RAM, latency и качество proposed lanes ещё не измерены и зависят от context size. До регулярного использования нужен локальный benchmark gate: peak RAM, latency и acceptance quality на типовом brief. Даже после PASS модель не становится автономным архитектором или надёжным orchestrator сложной multi-repo работы. Параллельный запуск нескольких тяжёлых локальных моделей не является default.

Kimi Code называется именно Kimi Code. Название `Kimi3` в plan, task briefs и отчётах не используется.

### 20.2 Task brief contract

Каждый delegated lane получает один короткий контракт:

| Поле | Требование |
|---|---|
| Цель | Один проверяемый outcome без скрытого расширения scope |
| Точные файлы | Явный allowlist путей на чтение и изменение |
| No-go zones | Файлы, данные и решения, которые нельзя трогать |
| Артефакт | Diff, JSON, fixture, report или test output |
| Команды проверки | Точные deterministic commands |
| Acceptance | Наблюдаемые условия PASS или FAIL |
| Data boundary | Запрет secrets и client data для cloud models |
| Review owner | Другой agent или человек, не автор изменений |

Агент не принимает собственную работу. Review идёт по diff и raw command output, а не по пересказу автора. Финальный reviewer проверяет только изменённые файлы и связанные contracts, затем выполняет integration checks. Любое изменение финансовой формулы, source trust type, CSP, storage access или publish policy требует strong-model review.

### 20.3 Метрики execution

Target значения устанавливаются после baseline, а не придумываются в PRD.

| Метрика | Формула | Сигнал |
|---|---|---|
| Доля детерминированных шагов | Шаги, закрытые script или test / все execution steps | Насколько workflow воспроизводим без модели |
| Primary-agent token use | Tokens primary agent по фазе и принятому artifact | Стоимость сложного reasoning |
| Rework rate | Повторно открытые задачи / принятые задачи | Качество briefs и review |
| Test pass rate | Успешные обязательные checks / все обязательные checks | Техническая готовность |
| Evidence completeness | Acceptance criteria с raw evidence / все acceptance criteria | Можно ли независимо принять результат |

Снижение tokens не считается успехом, если растут rework, пропущенные tests или неполные evidence records.
